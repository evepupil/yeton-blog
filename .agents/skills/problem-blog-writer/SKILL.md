# 问题复盘博客写作

## 目标与边界

- 固定目标仓库为 `C:\code\yeton-blog`，所有读取、写入和 Git 操作都在该目录进行。
- 一次调用产出同一篇文章的中文和英文版本，写入 `content/posts/zh/` 与 `content/posts/en/`。
- 正常调用代表用户要求发布：两篇文章均写 `draft: false`，门禁通过后提交并推送 `main`。用户明确要求草稿时才写 `draft: true`。
- 只改本次新增的文章及其专用图片。不要顺带修改项目代码、配置、路线图、模块文档或既有文章。
- 不启动开发服务器。

## 开始前

1. 遵循仓库现行 `AGENTS.md`；如根目录存在 `.codegraph/`，理解代码时先使用 CodeGraph。
2. 读取当前 `lib/content/schema.ts`、`docs/模块设计/内容系统.md` 和一组现有双语文章。当前代码与文档优先于本 Skill 中的字段示例。
3. 检查当前分支、`origin`、工作区状态以及 `HEAD` 与 `origin/main` 的关系。不要覆盖、暂存或提交用户已有改动。
4. 开始写作前执行 `git fetch origin main`。若本地已有未推送提交、分支发生分叉，或落后且无法在不处理用户改动的情况下更新，停止并说明原因。禁止强推和自动暂存用户改动。

## 事实要求

- 以用户提供的现象、报错、日志、代码、操作记录和验证结果为事实基础。可以读取用户明确放入范围的本地项目材料。
- 缺少会改变结论的关键信息时，只问一个简短问题并暂停写作。不得编造环境、命令输出、根本原因、修复效果、版本或亲身经历。
- 区分已确认原因和仍待确认的推测。无法验证的内容明确说明验证边界。
- 需要补充外部事实时优先查官方资料，并在文章末尾链接实际使用的页面。
- 写入前清理密钥、令牌、账号、内部地址、个人信息和可识别的业务数据。无法可靠脱敏时停止。

## 文件与元数据

- 为主题生成一个短小、稳定的小写英文 kebab-case 地址。默认让中英文文件共用该地址和 `.mdx` 后缀；创建前确认两个目标文件都不存在。
- 中英文使用相同的 `translationKey`。它必须是小写 kebab-case，且只在两篇文章同时落盘时写入。
- 新文章的元数据按以下顺序生成：

```yaml
---
title: "本语言标题"
description: "一到两句话概括问题、原因、处理办法和适用场景。"
published: "YYYY-MM-DD"
locale: "zh-CN"
tags:
  - "postmortem"
  - "现有标签"
draft: false
pinned: false
translationKey: "shared-translation-key"
---
```

- 中英文文章的标签都必须包含 `postmortem`。把它放在标签列表第一项，用户没有另外指定时也不得省略。
- 英文文章把 `locale` 改为 `en`，标题、摘要、其他标签和正文使用自然英文。
- `description` 必须非空且不超过 240 个字符；`tags` 至少一个、不得重复，并优先复用站内已有标签。
- 新文章省略 `updated`。只有后续实质修改才增加该字段，且日期不得早于 `published`。
- 只有真实本地封面已经写入仓库时才增加 `image`，路径必须以 `/` 开头。手工文章图片放在 `public/images/posts/<slug>/`。
- 永远不要为本 Skill 创建的文章写 `source: "notion"` 或 `notionPageId`。这两个字段会把文件交给 Notion 同步管理。
- 页面会根据这些字段自动生成 canonical、Open Graph、Twitter Card、作者信息和 `BlogPosting` 数据，不要在文章中重复维护。

## 标题

根据文章手里最硬的信息选择一种标题，不固定套问句：

1. 已确认根因：`<技术对象><具体原因>导致<故障结果>`，例如“PostgreSQL 纳秒精度导致幂等重放冲突”。
2. 排查过程最有价值：`<产品或组件><故障现象>排查与修复`，例如“MiniMax H3 Turbo 音频杂音与变声排查”。
3. 使用条件特殊：`<限制条件>下的<解决办法>`，例如“魔搭 GPU 无公网 IP 时的反向 SSH 接入”。
4. 报错文本有搜索价值：`<产品>的<关键报错>：<兼容性或原因>`，例如“ComfyUI 的 custom_op 报错：PyTorch 2.6 与 2.8 兼容性”。
5. 有真实对照数据：`<对象><现象>的<测试结论>`，例如“Vast.ai 停机后的 GPU 与磁盘计费窗口实测”。没有测试数据时禁用“实测”。
6. 问句只在用户原始问题本身很自然、且正文要解释一个反常原因时使用，例如“Vast.ai 停机后为什么还在扣费？”。默认优先前五种。

- 标题只承载“对象 + 问题 + 原因或处理方向”中的两项或三项，写成一句话。信息放不下就留给摘要，不用连续追问补齐。
- 已经确认根因时优先写判断句，不再用“为什么”；解决办法明确时可以写场景式标题，不再追加“怎么解决”。
- 不给文章标题套 `《》`，不同时使用“为什么”和“怎么解决”，不为了搜索词重复产品名、故障名和同义词。
- 一次需要提供多个候选标题时，使用不同模板给出三个。最多一个标题以问号结尾。
- 英文标题根据英文搜索习惯独立表达，保留同一问题和结论，不机械复制中文句式。

## 正文结构

- 页面会生成一级标题，正文不要再写 `#` 标题。
- frontmatter 后直接用两到三句话写清问题现象、确认原因、解决办法和必要限制。不要写“先说结论”“本文将”等提纲播报。
- 固定使用以下五个二级章节，并根据语言翻译标题：
  1. `## 问题详情`
  2. `## 排查与原因`
  3. `## 解决办法`
  4. `## 验证结果`
  5. `## 参考资料`
- 把有价值的无效尝试放入“排查与原因”，把适用范围和限制放入最相关的章节，不额外堆叠固定章节。
- 保留准确报错、环境、版本、命令、代码、失败过程和验证证据。长日志只摘录定位问题需要的部分。
- 体裁是问题复盘说明文：讲清故障怎样发生、处理办法为什么有效、边界在哪里。个人经历只作为证据，不展开成故事。
- 用同行口吻。默认读者懂基础概念，省掉客套和背景铺垫；项目特定术语首次出现时，用一句白话解释。
- 用日常词下明确判断。每个关键做法都要交代失效机制：不这么处理会在哪一步出错，结果会坏成什么样。
- 具体到能执行。优先写准确的报错、文件路径、字段、命令、版本、数字和验证结果，少用抽象概括。
- 一段只讲一件事，讲完就停。段落靠内容顺序连接，不写总起句、收尾句和升华段；各节篇幅按信息量分配，不追求整齐。
- 第一人称只用于用户真实提供的立场和动作。材料没有出现“我”的经历时，直接讲现象、机制和证据。
- 每句话都检查两遍：是否提供了事实、机制、原因、限制或后果；是否还能用更短的日常词表达。两项都不满足就删掉。
- 做万能句检验：把产品名换成另一个产品后仍然成立的句子，多半是空话，必须补具体机制或删除。
- 列表只承载真正并列的信息。一句话并列超过三项时拆开，只保留影响判断的内容。
- 冷幽默一篇最多两三处，不主动制造博主腔。
- 禁用“先说结论”“综上所述”“总的来说”“值得一提的是”“不难发现”“众所周知”“让我们”“其实”“说到底”“本质上”“核心在于”“真正的问题是”“很多人”“大家都”等套话和无依据泛化。
- 英文版保持同样的信息密度和同行口吻，按英语表达自然重写，不逐句硬译中文。
- 小标题使用读者会搜索的自然表达。关键结论写成脱离上下文仍能看懂的完整句子。
- 引用真实数据、直接引语或外部结论时给出来源。禁止关键词堆砌、虚构问答、虚构引用和重复改写同一句话。
- 仅在确有帮助时加入站内相关文章链接。中英文两篇的事实、命令、代码、图片、链接、结论和限制必须一致。

## 校验与发布

1. 只格式化本次新增的文章文件，不运行会改写整个仓库的格式化命令。
2. 依次运行 `pnpm content:check`、`pnpm format:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test` 和 `pnpm build`。
3. 检查 `git diff --check`，并人工核对中英文文章的元数据、事实一致性、引用链接、隐私信息和双语关联。
4. 任一门禁失败时修复本次文章造成的问题并重跑。失败来自仓库既有改动且无法安全处理时停止，不提交、不推送。
5. 仅暂存本次新增的中英文文章及专用图片。提交前核对暂存清单，禁止夹带用户文件。
6. 使用一条简洁的 `feat(content): ...` 提交信息提交，然后执行 `git push origin main`。
7. 推送遇到非快进时先获取远端。只有工作区干净且可以安全 rebase 时才执行 rebase；之后重跑门禁再推送。存在用户改动、冲突或不确定性时停止。禁止强推。

完成后用中文报告两篇文章路径、文章主题、门禁结果、提交号和推送结果。说明业务内容时使用中文含义，不使用代码字段名代替业务说明。
